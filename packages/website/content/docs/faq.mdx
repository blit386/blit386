Answers to the questions that come up most often. For live discussion, see the [Community](/community) page.

## WebGPU availability and browser support

### Which browsers support WebGPU?

Recent Chrome, Edge, Firefox, and Safari releases ship WebGPU; older versions either gate it behind a flag or lack it
entirely, in which case the engine falls back to the Canvas 2D software renderer.

The exact per-browser matrix is maintained with the engine and published at [Browser Support](/docs/api/browser-support)
\- that page is the single source of truth, so it is not duplicated here.

### What happens in a browser where WebGPU is not available?

The engine detects the missing API at startup and switches to the Canvas 2D software renderer automatically. No code
change is required. Use `BT.activeBackend` at runtime to check which backend is running (`webgpu` or `software`).

### Can I force the software renderer even in a WebGPU-capable browser?

Yes. Return `backend: 'software'` in the `HardwareSettings` object from your game's `configure()`, or append
`?backend=software` to the page URL during development.

### Does BLIT386 use WebGL instead of WebGPU?

No. The two backends are WebGPU and Canvas 2D. There is no WebGL backend. WebGPU and WebGL can coexist in the same
browser, but BLIT386 does not use WebGL.

## Software fallback

### Are all features available in the software renderer?

All but one. Palette resolution, integer coordinates, sprite rendering, input, and audio (Web Audio only, never the GPU)
behave the same on both backends. The exception is post-process effects (CRT scanlines, bloom, barrel distortion, etc.),
which need WebGPU. In software mode `BT.effectAdd()` does not throw: it reports the error once (a panel in dev builds,
the console in release) and adds nothing, so a `try`/`catch` fallback around it never runs. Gate effect calls on
`BT.activeBackend === 'webgpu'` instead. See [API: Rendering](/docs/api/rendering) for details. The engine overlay shows
the active backend in its renderer diagnostics bar.

### How do I test fallback behavior locally?

Append `?backend=software` to the dev-server URL, or return `backend: 'software'` from `configure()`. The
[Software Fallback Smoke Matrix](/docs/performance/smoke-matrix) lists the manual checklist used to verify parity.

## Setup and installation

### What is the minimum Node.js version?

Node.js >= 22.18.0 (LTS). The engine is published as an ESM package and requires a bundler such as Vite, webpack, or
esbuild to serve it in a browser.

### What is the quickest way to start a new project?

Use the scaffolder:

```bash
npm create blit386@latest my-game
```

This generates a ready-to-run Vite project with the engine, a starter game, and the `blit` project CLI. See
[Getting Started](/docs/getting-started) for the full walkthrough.

### The demo page is blank and there is no error in the console. What should I check?

- Verify that `bootstrap()` is called and that the canvas element ID matches `BootstrapOptions.canvasID` (default:
  `blit386-canvas`).
- Check that `BT.paletteSet()` is called in `init()` before any draw calls in `render()`.
- Open the browser DevTools Network tab and confirm that sprite sheets and font files loaded successfully.
- Check `BT.activeBackend` - if it is `null`, the engine has not finished initializing yet.

### I am getting a TypeScript error about unknown properties on `HardwareSettings`. What is happening?

Some configuration fields were renamed in 1.1.1 to follow the `is*`/`has*` boolean-naming convention (1.2.0 was a
different change: the npm package rename from `blit-tech` to `blit386`). The old names are available as compatibility
aliases until the next major release. See the [Deprecation Timeline](/docs/reference/deprecations) for the full mapping
and the [Changelog](/docs/reference/changelog) for the release history.

## Audio

### Why is there no sound?

Browsers refuse to start audio until the user interacts with the page, so BLIT386 starts in a locked state. On
`BT.init()` the engine listens on the canvas for `pointerdown`, `pointerup`, `touchend`, and `keydown`: the first click,
key press, or tap (a tap counts when the finger lifts) unlocks the audio context for the rest of the session, and
`BT.isAudioUnlocked` flips to `true`.

The two playback paths behave differently while still locked:

- `BT.soundPlay()` is dropped - it returns an inert `SoundRef` and no voice is allocated.
- `BT.musicPlay()` is remembered and starts automatically the moment the context unlocks.

Loading is unaffected: `AudioClip.load()` and `AudioClip.synth()` both work while locked, because decoding does not need
an unlocked context. If a game must make noise immediately, either wait for `BT.isAudioUnlocked`, or prompt for a click
or key press first. See the [Audio Guide](/docs/guides/audio).

## Reporting

### Where do I report bugs or ask questions?

Open an issue on [GitHub](https://github.com/blit386/blit386/issues) or start a thread in
[GitHub Discussions](https://github.com/blit386/blit386/discussions). Please include your browser version, operating
system, and a minimal reproduction.
